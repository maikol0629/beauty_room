# AGENTS.md — Beauty Room

Backend Spring Boot (Java 21, Boot 3.2.3, MariaDB) para agendamiento de citas en salones de belleza. SaaS multitenant (Fase 0 COMPLETADA) con bot de Telegram (Fases 2-5 COMPLETADAS). Toda la documentación del proyecto está en español en la raíz.

## Comandos
- Ejecutar la app: `./mvnw spring-boot:run` (desde la raíz)
- Compilar: `./mvnw -DskipTests compile`
- Tests: `./mvnw test` (para un test solo: `./mvnw test -Dtest=NombreClase`)
- Levantar MariaDB: `docker-compose up -d` desde `src/main/resources/`
- No hay lint ni formatter configurado. La verificación es compile + tests.

## Base de datos (gotchas)
- Local: db `beauty_room`, user `dev` / `dev123` en `localhost:3306` (definidos en `src/main/resources/docker-compose.yml`). Tests usan `beauty_room_test` (misma credencial).
- **Flyway ACTIVO (Fase 2 del plan de mejora COMPLETADA):** el esquema es fuente de verdad en `src/main/resources/db/migration/` (`V1__init_schema.sql` esquema exacto de Hibernate + `V2__seed_data.sql` seed idempotente). Perfiles `dev`/`staging`/`prod` usan `ddl-auto=validate` + Flyway con `baseline-on-migrate=true`. `V1__init_schema.sql` debe mantenerse en sintonía con las entidades (Hibernate valida contra él).
- Perfiles: `spring.profiles.active=${SPRING_PROFILES_ACTIVE:dev}`. Existen `application-{dev,test,staging,prod}.properties`. `staging`/`prod` exigen `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` desde env (sin fallback); `test` usa la db `beauty_room_test`.
- `test` es el ÚNICO perfil con `create-drop` + `import.sql` (aislamiento por contexto). OJO: `src/test/resources/application.properties` hace SHADOW del `application.properties` de la app y bloquea la importación del `.env` del proyecto, así los tests SIEMPRE usan perfil `test` + `beauty_room_test`. NO borres ese archivo ni agregues `@ActiveProfiles` redundante.
- El `.env` local (gitignored) puede forzar `DDL_AUTO=create-drop`/`FLYWAY_ENABLED=false`/`MySQLDialect` si el desarrollador lo dejó de la era pre-Flyway: la app arranca igual (create-drop), pero para adoptar Flyway en local seguir `.env.example` (que ya recomienda `MariaDBDialect`, `DDL_AUTO=validate`, `FLYWAY_ENABLED=true`).
- OJO dialécto: usar `org.hibernate.dialect.MariaDBDialect` (fallback por defecto). `MySQLDialect` falla `ddl-auto=validate` contra MariaDB 12.x ("missing table" aunque las tablas existan).
- Los tests `@DataJpaTest` y `@SpringBootTest` usan la MariaDB real (`@AutoConfigureTestDatabase(replace = NONE)`); necesitan la DB corriendo. Los tests de Services usan Mockito y no la requieren.
- `import.sql` (y su gemelo `V2__seed_data.sql`) siembra 3 tenants (ids 1-3: Salón María `salon-maria-001`, Estilos Ana `estilos-ana-001`, Beauty Room Pro `beauty-room-pro-001`) y users con ids 1-4 (hash BCrypt de `password`); `Stylist`/`Client` reutilizan el mismo `id` que `users`. john@example.com y alice@example.com → tenant 1; jane@example.com y bob@example.com → tenant 2.

## Arquitectura
- Paquete base `com.mr.sb.beauty_room`: `controllers/`, `services/` (interfaces `I*`), `services/implement/` (`*ServiceImplement`), `repository/`, `entities/`, `dto/`, `security/`, `exceptions/`.
- Patrón: Controller → interfaz `IService` → `*ServiceImplement` → Repository. Nuevas features siguen este patrón.
- DTOs unificados a camelCase (Fase 3 del plan de mejora): TODOS los campos de DTO (request y response) son camelCase (`clientId`, `stylistId`, `serviceId`, `telegramChatId`, `nameClient`...). NUNCA uses snake_case en DTOs nuevos. OJO: los campos de las entidades JPA son camelCase (`nameClient`, `telegramChatId`, `nameService`), y las COLUMNAS de BD quedan snake_case vía `SpringPhysicalNamingStrategy` (default de Boot). No pongas `@Column` con nombre salvo que difiera.
- `User` es la entidad base con herencia JOINED; `Stylist` y `Client` extienden `User`. `Role` es enum (CLIENT, STYLIST, ADMIN).
- Fase 8 de normalización de nombres COMPLETADA (ver `docs/analisis-nombres-fase8.md`): la entidad de negocio es `SalonService` (no `Service`, para no chocar con `@Service`), `StylistScheduleServiceImplement` (typo corregido), campos de entidades camelCase, paquetes en minúsculas (`dto`, `services`, `controllers`, `security`, `config`, `exceptions`).
- Estándares de código vigentes: inyección por constructor vía Lombok `@RequiredArgsConstructor` (NO `@Autowired` ni constructores manuales), imports explícitos (sin `import ...*;` de paquetes del proyecto, ej. `entities.*`/`repository.*`), sin FQN de anotaciones (usar `import org.springframework.stereotype.Service` + `@Service`), sin trailing whitespace.
- Seguridad: JWT (jjwt 0.11.5) vía `JwtAuthenticationFilter`; endpoints públicos listados en `SecurityConfig`. El secret viene de `${JWT_SECRET_KEY:...}` con fallback hardcodeado en `application.properties` (pendiente de externalizar por completo en el plan de mejora).

## Multitenant (Fase 0 — COMPLETADA)
- Entidad `Tenant` + enums `TenantPlan`/`TenantStatus`. Toda entidad de negocio tiene `@ManyToOne(fetch = LAZY) Tenant tenant` con `@JsonIgnore` (NO `@JsonBackReference`).
- Resolución por request: `TenantInterceptor` (en `security/`) lee el claim `tenantId` del JWT; si no hay JWT, usa el header `X-Tenant-ID`. Guarda en ThreadLocal; `getCurrentTenantIdOrThrow()` lanza `TenantNotResolvedException` (manejada como 400). Registrado en `config/WebConfig` para `/api/**`.
- Services y repositorios filtran por tenant SIEMPRE. Los tests de aislamiento: `TenantIsolationTest` (usa `setCurrentTenantId`/`clear`) y `TenantJwtFlowTest`.
- `jackson-datatype-hibernate6` está en `pom.xml` para serializar proxies lazy sin errores.
- OJO con queries derivadas: `NotificationRepository` usa `findByTenantIdAndUserIdOrderByCreatedAtDesc` (el nombre invertido no compila como query derivada).
- `IBlockedSlotService.isSlotBlocked(Long tenantId, Long stylistId, ...)` recibe tenantId como primer parámetro.
